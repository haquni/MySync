# Архитектура MySync

## Статус

Документ задаёт направление архитектуры на основании README. Реализованы расчёт
SHA-256, сканирование и сравнение, план первой синхронизации, SQLite-состояние,
JSON-конфигурация, безопасная запись новых файлов, резервирование перед удалением,
UDP-обнаружение, TCP-сессия первого объединения и CLI. Сетевой MVP умеет
передавать уникальные файлы и пустые каталоги в обе стороны, не изменяя
конфликтующие пути. Удаления, замена файлов, установка и фоновая работа пока
не реализованы.

## Структура

```text
src/
  mysync/
    __main__.py         # запуск через python -m mysync
    cli.py              # команды init/serve/devices/sync/status
    __init__.py
    application/
      __init__.py
      initial_sync.py   # безопасный план первого объединения
      service.py        # обнаружение, сервер и подключение
      session.py        # строгий двусторонний TCP-сеанс
    core/
      __init__.py
      hashing.py
    filesystem/
      __init__.py
      backup.py         # резервирование и безопасное удаление
      scanner.py        # снимок корневой папки
      comparison.py     # сравнение двух снимков
      receiver.py       # проверенная запись нового файла
    network/
      __init__.py
      discovery.py      # UDP-объявления устройств
      messages.py       # служебные JSON-кадры поверх TCP
      transfer.py       # потоковые байты файлов
      transport.py      # TCP listener/client
    storage/
      __init__.py
      config.py         # JSON-конфигурация устройства
      database.py       # SQLite-состояние и история файлов
tests/
  test_backup.py
  test_config.py
  test_database.py
  test_hashing.py
  test_receiver.py
  test_scanner.py
  test_comparison.py
  test_initial_sync.py
docs/
  architecture.md
pyproject.toml
```

Исходники приложения размещаются в пакете `mysync` внутри `src/`.
Учебный пример не является частью библиотеки и не импортируется при её загрузке.
Импорт пакета не запускает сканирование, сеть или запись файлов.
Первый шаг использует только стандартную библиотеку Python, включая unittest.

## Границы компонентов

- `core` — хеширование, модели состояния и планирование операций.
- `filesystem` — сканирование, временные файлы и резервные копии.
- `storage` — локальная SQLite-база и JSON-настройки.
- `network` — обнаружение, служебный протокол и передача по TCP.
- `application` — координация сканирования, первого объединения и сетевой сессии.
- `cli` — первичная настройка и ручное управление тестовым MVP.
- `platforms` — автозапуск и открытие терминала на Windows/Linux.

Первые шесть областей уже представлены кодом; `platforms` остаётся будущим
компонентом. Ядро не зависит от CLI, сети или особенностей платформы.
Прикладной слой связывает компоненты; сетевой код не определяет правила
удаления файлов.

## Контракт хеширования

```python
from mysync.core.hashing import sha256_file

digest = sha256_file(path)
```

`sha256_file(path: pathlib.Path) -> str` читает файл в бинарном режиме
блоками не более 1 МиБ и возвращает 64 символа SHA-256 в нижнем регистре.
Пустые, бинарные файлы, Unicode и пробелы в пути поддерживаются.
Файл не изменяется; дескриптор закрывается и при ошибках чтения.
Ошибки файловой системы (например FileNotFoundError, PermissionError,
IsADirectoryError) передаются вызывающему коду без замены пустым результатом.

Результат описывает прочитанный поток байтов. Защита от одновременного изменения
файла будет обязанностью будущего сканера; этот модуль не создаёт снимок файла.

## Контракт сканера

`scan_directory(root: pathlib.Path) -> ScanResult` возвращает отсортированные
записи файлов и каталогов с относительными путями через `/`. Каждый файл
содержит размер, `mtime_ns` и SHA-256. Пустые каталоги представлены явно.
Сканер не следует по символическим ссылкам. Если файл меняется во время
хеширования, он сообщает об ошибке вместо неполного снимка. Столкновения
имён без учёта регистра также считаются ошибкой. Специальные объекты вроде
FIFO отвергаются до чтения, чтобы не заблокировать проход. Полный контракт — в
`docs/tasks/TASK-002.md`; это локальный артефакт работы агентов.

## Контракт сравнения

`compare_snapshots(before, after) -> SnapshotDiff` сравнивает файлы по
относительному пути без учёта регистра и SHA-256. Результат содержит четыре
группы: добавленные, отсутствующие в новом снимке, изменённые и неизменённые.
Разница только во времени изменения при одинаковом хеше не считается изменением
содержимого. Изменение только регистра имени отмечается отдельно как изменение.
`missing` не является командой удаления: для этого нужна история синхронизации.
Каталоги пока не сравниваются.

## План первого объединения

`plan_initial_sync(left, right) -> InitialSyncPlan` определяет копирование
уникальных файлов в обе стороны, создание отсутствующих каталогов и конфликты.
Одинаковые по пути, но разные по содержимому файлы не перезаписываются.
Файл и каталог с одним относительным путём образуют структурный конфликт;
операции в его поддереве исключаются из автоматического плана. Отсутствие
файла при первом объединении не означает удаление. План не пишет на диск
и не содержит сетевого протокола.

## Локальное состояние

`StateDatabase` хранит устройства и отдельный снимок файлов для каждого из них.
При сохранении полного снимка транзакционно создаются события `created`,
`modified` и `deleted`. Повторное сохранение тех же данных идемпотентно.
Таблицы конфликтов и запусков синхронизации созданы для следующих этапов.

`AppConfig` хранит корневую папку, UUID и имя устройства, TCP/UDP-порты,
срок хранения резервов и автоматический режим. JSON имеет версию схемы,
строго проверяется и заменяется атомарно.

## Безопасные файловые операции

`receive_new_file` записывает бинарные блоки во временный файл, проверяет
SHA-256 и атомарно устанавливает только новый файл. Существующий файл не
перезаписывается. Пути с выходом за корень и символические ссылки отклоняются.

`backup_existing_file` и `delete_with_backup` сохраняют пользовательский файл
под `_mysync/backups` до удаления. `purge_expired_backups` удаляет резервы старше
заданного срока. Служебные файлы `_mysync` рекурсивно не резервируются.

## Базовый сетевой протокол

`DiscoveryEndpoint` явно открывает управляемый вызывающим кодом IPv4 UDP-сокет.
Узел отправляет ограниченное 2048 байтами JSON-объявление версии 1 с UUID,
именем и TCP-портом. Входные пакеты строго проверяются, а объявления с UUID
текущего устройства игнорируются. Сам факт обнаружения не делает устройство
доверенным и не запускает синхронизацию.

`send_message` и `receive_message` обмениваются служебными JSON-сообщениями через
уже установленный TCP-сокет. Перед телом передаётся четырёхбайтовая длина
big-endian; тело ограничено 1 МиБ. Модуль корректно собирает частичные чтения,
отличает преждевременное закрытие соединения от ошибки протокола и не закрывает
сокет вызывающего кода. Открытие TCP-сервера, передача файлов, доверие и повторы
относятся к следующим задачам.

`DiscoveryResponder` слушает общий UDP-порт 37841 и отвечает на объявление
инициатора. `discover_devices` собирает ответы без ручного ввода адресов и
портов. Постоянный `serve` одновременно обслуживает обнаружение и
последовательные TCP-сеансы.

`run_client_session` и `run_server_session` обмениваются идентичностями и
полными снимками, строят одинаковый план первого объединения и выполняют две
фазы передачи по одному соединению. Метаданные передаются JSON-кадрами, а
содержимое — ограниченными блоками сырых байтов. Размер и SHA-256 проверяются
до установки. Конфликты возвращаются в `SyncResult`, но не изменяются.

## Проверка

Из корня проекта, без установки зависимостей:

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

```powershell
$env:PYTHONPATH = "src"
python -m unittest discover -s tests -v
```

## Решения для следующих этапов

Перед реализацией следующих компонентов нужно уточнить их контракты:

- отличать начальное объединение файлов от последующих удалений по истории;
- определить время удаления: сканер видит отсутствие файла, а не точное время удаления;
- согласовать автоматический выбор поздней версии и случаи ручного конфликта;
- определить поведение пустых каталогов, удаление которых отдельно не отслеживается;
- отделить локальную базу и идентичность от синхронизируемых данных `_mysync`;
- исключить рекурсивное создание резервных копий и бесконечный обмен журналами;
- подобрать механизм обнаружения при автоматически выбранных TCP-портах;
- определить способ скрытия `_mysync` на Linux: универсального атрибута Windows hidden там нет;
- определить начальный запуск команд сборки до установки программы.

Эти вопросы не препятствуют текущим модулям чтения и сравнения.
